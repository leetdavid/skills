# Commander's intent

Establish enough shared intent that someone can choose and adapt their approach without asking for instructions at every step. Use ordinary workplace language and keep the brief short enough to read aloud.

## Workflow

1. Read the request and available context. Extract stated goals, essential tasks, constraints, and success conditions. Infer the audience from the conversation using the guidance below.
2. Draft the three-part brief before asking questions. Use what is already known. Label an inferred goal or suggested requirement **Proposed** beside the claim; mark missing information **To confirm**. Dates, metrics, owners, and approvals need the same treatment.
3. Ask only questions whose answers could change the purpose, essential work, scope, trade-offs, or definition of success. In a standalone conversation, ask up to three questions per round, starting with the biggest gaps. Give a recommended answer when the context supports one, and explain the practical consequence of the choice. Reuse answers already given.
4. Surface contradictions between the requested work, constraints, and intended outcome. Keep explicitly required methods as constraints unless the person setting them agrees they are flexible. When a trade-off exceeds the team's authority, identify who needs to decide rather than choosing for them.
5. Revise the brief as answers arrive. Finish when the purpose explains the priorities, the key tasks cover the essential work, and the end state makes success recognizable. When answers are unavailable, return a provisional brief with the consequential gaps still visible. Describe intent as agreed only when the relevant people have confirmed it.

Settle intent before asking about implementation details. If the supplied context already settles it, produce the brief directly. When another planning or interviewing workflow is active, use this brief to focus its questions and follow its question format.

## Brief

Use these three headings. Include a short **To confirm** list afterward only when material gaps remain.

### Purpose

Why does this work matter, for whom, and what larger outcome does it support? Write one or two sentences that help choose between competing approaches. If the request only names a deliverable, establish the reason behind it.

### Key tasks

List the few actions essential to achieving the purpose, in priority order when known. Test each item: would omitting it defeat the intent? Leave the execution sequence and detailed task breakdown to the plan. Keep supplied constraints visible next to the work they govern.

### Desired end state

Describe what must be observably true when the work is complete. Include what must still be true, such as uninterrupted service, when relevant. Use supplied success measures and deadlines; propose missing criteria explicitly. Make it possible to judge the result beyond whether the task list was completed.

## Adapt to the conversation

- **Clarifying work with the user:** Present your current understanding first. Direct questions to the user about the consequential gaps, then carry the resulting intent into planning. Leave implementation choices open where the intent permits them.
- **Planning with teammates:** Draft a shared brief for discussion. Surface competing interpretations and distinguish shared requirements from choices each teammate can make independently. Record owners or dependencies when supplied or agreed; label suggestions as proposals.
- **Receiving instructions from a boss:** Separate the actual instruction from your interpretation. Help the user prepare a concise read-back in their own voice, followed by focused clarification questions. If the requested approach conflicts with the outcome, explain the concrete trade-off respectfully. Treat the read-back as a request for confirmation, not evidence that the boss has agreed.

If circumstances change, use the purpose and end state to reassess the plan. Changes to the intent or agreed constraints need renewed alignment with the people who set them.

## Example

User: My boss said, "Move support to the new helpdesk by Friday. Keep customers supported throughout."

### Purpose

To confirm: what problem the helpdesk change is intended to solve.

### Key tasks

- Move the support workflow to the new helpdesk by Friday.
- Maintain customer support during the transition.

### Desired end state

By Friday, the new helpdesk handles the agreed support scope, and customers have retained access to support throughout the transition. The required scope and evidence of a successful move still need confirmation.

### To confirm

- Which problem should this change solve? That will guide what to prioritize for Friday.
- What must be working in the new helpdesk for the move to count as complete, including any required channels or request history?

Suggested read-back: "My understanding is that we're moving support to the new helpdesk by Friday while keeping customers supported throughout. Which problem should the change solve, and what must be working by Friday for you to consider the move complete?"
